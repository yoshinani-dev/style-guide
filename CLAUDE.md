# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

`@yoshinani/style-guide` is a **shared linting/formatting configuration package**, not an application. The oxfmt / oxlint / commitlint configs are written in TypeScript under `src/` and built with Vite+ (`vp pack`, tsdown, unbundled) into `dist/` as `.mjs` + generated `.d.mts`; `typescript/*.json` and `cspell/` ship verbatim. The test suite runs oxlint against fixtures to check the built configs. Changes here are config edits that downstream consumers `extends`. The package documentation (README.md, CONTRIBUTING.md) is written in Japanese; rule rationales link to an internal Notion.

## Commands

```sh
mise install        # install Node 24 + pnpm 10 (versions pinned in mise.toml)
pnpm install
pnpm check          # vp check — format + lint + type check (tsgolint) (CI)
pnpm check:fix      # vp check --fix
pnpm build          # vp pack — build src/ into dist/ (also runs on prepack)
pnpm test           # vp pack && vp test — runs oxlint against tests/fixtures/* using dist/ (CI)
pnpm test:tsconfig  # compile tests/fixtures/typescript/* with the shared tsconfigs (CI also runs it on TS 6 and 7)
pnpm changeset      # record a version bump; required for any user-facing change
```

`pnpm check`, `pnpm test` and `pnpm test:tsconfig` together match CI (`.github/workflows/check.yml`). All repo tooling config (fmt, lint, pack, test) lives in `vite.config.ts`, which lints and formats the repo with the configs in `src/` (dogfooding). Commits are validated by a husky `commit-msg` hook running commitlint.

## How configs are exposed

`package.json` `exports` is **generated by `vp pack`** (tsdown `exports` in `vite.config.ts`): every `src/**/*.ts` entry becomes a subpath (`src/oxlint/next.ts` → `./oxlint/next`, `src/oxfmt/index.ts` → `./oxfmt`, `src/commitlint/index.ts` → `./commitlint`), and `customExports` adds the raw `typescript/*.json`. Don't hand-edit `exports`; run `pnpm build` and commit the regenerated `package.json`. TypeScript finds the `.d.mts` next to each `.mjs`, so no `types` condition is needed. `files` whitelists `dist`, `typescript`, `cspell`. Consumers reference them as e.g. `@yoshinani/style-guide/oxlint/library`, `@yoshinani/style-guide/oxfmt`, `@yoshinani/style-guide/typescript/next`.

## oxlint architecture (the core of this package)

`src/oxlint/base.ts` holds all the opinionated rules and is the single source of truth. Configs are plain config objects that consumers pass to `extends` in their own `oxlint.config.ts` (`.oxlintrc.json` cannot import packages). The other entry points spread `base` and layer on environment globals / framework rules:

- `base.ts` — `categories.correctness: "error"` plus the rules carried over from v1 (eslint:recommended, typescript-eslint recommendedTypeChecked, org rules), `options.typeAware: true`, `no-process-env`, enum ban, `no-restricted-imports`, `import/no-duplicates`.
- `library.ts` — `base` + node globals.
- `react-library.ts` — `base` + `rules/react.ts` + browser/service-worker globals.
- `next.ts` — `base` + `rules/react.ts` + every rule of oxlint's `nextjs` plugin as `error`. oxlint has no per-plugin presets; all `nextjs` rules are in the `correctness` category, so adding the plugin on top of base's `correctness: "error"` enables them. A test compares `oxlint --rules` with `oxlint --print-config` and fails if any `nextjs/*` rule is not `deny` (e.g. a future rule in another category), App Router overrides (special files need a default export; image-generation files may use `<img>`), browser + node globals.
- `*-effect.ts` (`base-effect`, `library-effect`, `react-library-effect`, `next-effect`) — the matching entry point + `rules/effect.ts`, which pulls in `@effect/tsgo`'s `recommended` oxlint preset (Effect v4 only) and turns off `effecttsgo/unstable-api-usage` in test files. `effecttsgo` is not a stock oxlint plugin: it only loads under an Effect-patched oxlint (`effect-tsgo patch --oxlint --no-typescript`) or via `effect-tsgo oxlint`, so the tests run the Effect fixtures through that wrapper. `@effect/tsgo` pins the oxlint / oxlint-tsgolint versions it supports — keep them in step (dependabot groups them).
- `rules/react.ts` — React rule block (oxlint's `react` plugin includes the react-hooks rules), shared by `react-library.ts` and `next.ts`.
- `rules/restricted-imports.ts` — the banned-library lists, exported so consumers can extend them (oxlint replaces rule options instead of merging).
- `plugins/yoshinani.ts` — a local JS plugin for rules oxlint lacks: `yoshinani/require-description` (covers both `eslint-disable` and `oxlint-disable`) and `yoshinani/no-enum`. `base.ts` references it by absolute path (keeping the importing module's extension, so it points at `.ts` in `src/` and `.mjs` in `dist/`) so it resolves when extended from a consumer's config.

Composition gotchas (verified against oxlint 1.89 / 1.90): `extends` only carries `rules`, `plugins`, `overrides` (and `categories` / `options` in practice) — top-level `env` / `globals` are dropped, so environment globals go in an `overrides` entry with `files: ["**/*"]`. The fixtures under `tests/fixtures/` have their own `oxlint.config.ts` (extending `dist/`) and intentionally violate rules; `vite.config.ts` ignores them. Under `vp test`, Vite+ sets `VP_VERSION`, which makes a child `oxlint` look for a `vite.config.ts` `lint` block — the tests strip it before spawning oxlint.

`no-restricted-imports` encodes the org's **opinionated tech-stack choices**: e.g. zod/yup/joi → Effect Schema or valibot, lodash → remeda, axios → fetch, moment/dayjs → date-fns, MUI/emotion → shadcn+Tailwind, jest → vitest, redux/recoil → zustand/jotai. When adding library bans, follow this existing pattern in `rules/restricted-imports.ts` (name with a Japanese `message` pointing to the preferred alternative).

Type-aware rules run through `oxlint-tsgolint` (typescript-go), so consumers need dependencies installed and a resolvable `tsconfig.json`.

## Other configs

- **oxfmt** (`src/oxfmt/index.ts`) — formatter config object: no semicolons, double quotes, printWidth 80, import sorting (`sortImports` groups: builtin → external → `@repo/**` → alias → relative), Tailwind class sorting, Markdown excluded. oxfmt has no `extends`, so consumers spread it into their own `oxfmt.config.ts` (only `.ts` / `.oxfmtrc.json` are auto-discovered) or into the `fmt` block of a Vite+ `vite.config.ts`. The repo's own `vite.config.ts` spreads `src/oxfmt/index.ts` unchanged except for repo-specific `ignorePatterns`.
- **TypeScript** (`typescript/base.json` + `next.json`, `react-library.json`, and `effect.json` / `next-effect.json` / `react-library-effect.json`) — strict, `noUncheckedIndexedAccess`, NodeNext base, `"types": []` (TypeScript 7's default, made explicit so TS 5 / 6 / 7 behave the same; the variants inherit it — `next.json` no longer adds `vitest/importMeta`, since that broke projects without vitest); variants override module/jsx. Supported on TypeScript 5 / 6 / 7: `tests/tsconfig.ts` compiles `tests/fixtures/typescript/*` (with `@ts-expect-error` lines proving `types: []` and `exactOptionalPropertyTypes` take effect) and CI runs it on each major via `pnpm --package=typescript@N dlx node tests/tsconfig.ts`. The `-effect` variants add the `@effect/language-service` plugin (diagnostics off; oxlint reports them) and `exactOptionalPropertyTypes`. `compilerOptions.plugins` is replaced, not merged, on `extends`, so `next-effect.json` re-lists the `next` plugin.
- **commitlint** (`src/commitlint/index.ts`) — conventional commits with a **restricted** `type-enum`: only `build`, `docs`, `feat`, `fix`, `refactor`, `test`, `release` (`release` is reserved for automated releases).

## Vite+ and tool versions

Consumers can use the configs either from a Vite+ `vite.config.ts` (`fmt` / `lint` blocks) or with standalone oxfmt / oxlint config files — README documents both. Vite+ pins exact oxlint / oxfmt / oxlint-tsgolint versions, and the repo's devDependencies `oxlint`, `oxlint-tsgolint` and `@oxlint/plugins` are pinned to the same versions (a test fails if they drift), so the standalone tests and `vp check` exercise one toolchain. `oxfmt`, `oxlint`, `oxlint-tsgolint` and `vite-plus` are optional peers.

## Release flow

Versioning is via **Changesets**. Any change affecting consumers needs `pnpm changeset` committed in the PR; merging to `main` triggers the release GitHub Action which version-bumps, updates CHANGELOG, and publishes (`prepack` runs `vp pack`, so `dist/` is built on publish). Do not hand-edit `version` in `package.json` or `CHANGELOG.md`.

## CI と検査（yoshinani 共通ルール）

GitHub Actions では検査を実行しない。検査はすべてローカルで行う（正本: [CI_POLICY.md](https://github.com/yoshinani-dev/.github/blob/main/CI_POLICY.md)）。

- `pnpm verify`: `git push` のたびに pre-push フックで自動実行される。失敗すると push できない。中身: `pnpm run check && pnpm run test:tsconfig && pnpm run test`
- `pnpm verify:full`: PR をマージする前に必ず実行し、結果を PR の「テスト項目」に書く。中身: `pnpm run verify && pnpm --package=typescript@6 dlx node tests/tsconfig.ts && pnpm --package=typescript@7 dlx node tests/tsconfig.ts && git diff --exit-code package.json`
- フックが動かないときは `pnpm install` を一度実行する（`prepare` で有効になる）
- `git push --no-verify` は緊急時だけ。使ったら PR に理由を書く
- 依存パッケージは月1回ローカルで更新する（`pnpm update` → `pnpm verify:full`）。Dependabot のバージョン更新は使わない（脆弱性アラートだけ有効）
- Actions に検査用のワークフローを追加しない（置いてよいのは PR の自動ラベル付け・デプロイ・リリースだけ）
